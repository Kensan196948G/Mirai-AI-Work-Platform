# 障害対応手順

**文書状態：設計段階**  
**対象：Mirai AI ワークプラットフォーム Pilot運用**

## 1. 目的

本書は、利用不能、データ破損、セキュリティ事象、外部API障害、ストレージ障害が発生した際に、被害拡大を防ぎ、証拠を保全し、安全に復旧する手順案を定める。連絡先、RPO/RTO、正式な重大度と承認者はPilot開始前に確定する。

## 2. 重大度案

| 重大度 | 例 | 初動 |
|---|---|---|
| 重大 | 不正アクセス、データ破損、10TB HDD故障、全面停止、Secret漏えい | 新規処理停止、責任者招集、証拠保全 |
| 高 | 一部機能停止、継続的I/Oエラー、認可異常、backup連続失敗 | 影響機能の隔離、原因切分け、復旧判断 |
| 中 | 性能低下、単発Job失敗、容量85%以上 | 回避策、監視強化、期限付き修正 |
| 低 | 利用影響の小さい警告 | 通常Issueとして追跡 |

## 3. 共通初動

1. 検知時刻、報告者、症状、対象User/Project、Request IDを記録する。
2. Security、データ破損、書込み継続による悪化を最優先で評価する。
3. 必要に応じてUpload、Agent、Artifact生成等の新規書込みを停止する。
4. ログ、監査、kernel情報、version、mount状態を読み取り中心で保全する。
5. 影響範囲と利用者向け連絡を決める。
6. 復旧策とrollback条件を承認者へ提示する。

原因不明のままサービス再起動、filesystem修復、ログ削除、バックアップ上書きを繰り返さない。

## 4. 10TB HDD未接続・未マウント

1. アプリケーションがfail-closedで新規書込みを停止していることを確認する。
2. `/mnt/storage` を通常ディレクトリとして使っていないこと、OSルート容量が増えていないことを確認する。
3. 期待する型番、シリアル、UUIDと接続状態を確認する。
4. kernel log、電源、USB cable/bridgeを確認する。無闇な抜差しを繰り返さない。
5. 正しいHDDが正常にmountされ、read-write、空き容量、簡易readが正常であることを確認する。
6. 監査・File metadataとの整合を確認してから段階的に書込みを再開する。

別デバイスを同じパスへmountして復旧扱いにしない。期待UUID不一致は未mountと同じく停止条件とする。

## 5. read-only・I/O・filesystem異常

1. 新規書込みとAgentを停止し、可能なら影響HDDを読み取り中心に扱う。
2. kernel error、S.M.A.R.T.、発生時刻、対象ファイルを記録する。
3. 重要データの別系統バックアップと最終成功時点を確認する。
4. 修復操作前に、可能な範囲でイメージ保全または専門判断を行う。
5. `fsck` 等はunmount、対象デバイス照合、バックアップ確認、承認後に実施する。
6. 健全性に疑いが残るHDDを継続運用へ戻さず、交換・復元を検討する。

## 6. 容量逼迫

- 85%：増加源、Temp、失敗Job、ログを確認し、移行計画を具体化する。
- 90%：大容量UploadとJobを制限する。
- 95%：緊急保護モードへ移行する。

削除はTemp等の承認済み保持ルールから行い、監査ログ、DB、未知ファイルを緊急削除しない。個別Quotaを増やして全体予備を侵食しない。

## 7. 別系統バックアップからの復元

1. 復元時点と業務影響をData Ownerと決定する。
2. バックアップの暗号化鍵、checksum、対象、世代を確認する。
3. 原本を上書きせず隔離した復元先へ展開する。
4. ファイル件数、総バイト数、checksum、DB整合、権限を検証する。
5. 欠落期間と再入力・再実行対象を特定する。
6. 承認後に切替え、監視を強化する。

既存4TB HDDは10TB全体の完全バックアップとみなさず、保存対象と健全性が確認できる場合だけ限定的な復旧元として扱う。

## 8. アプリ・DB・DeepSeek障害

- アプリ障害：対象version、直前変更、5xx、依存service、Storageを確認し、必要なら前versionへrollbackする。
- DB障害：新規書込みを抑制し、接続、容量、migration、backupを確認する。安易に再初期化しない。
- DeepSeek障害：再試行上限を守り、Jobを無限実行せず、利用者へ外部障害を表示する。未完成Artifactを成功扱いしない。

## 9. セキュリティ事象

疑わしい主体・資格情報を失効し、影響範囲を隔離する。監査ログ、access log、設定変更、外部送信を保全し、関係者へエスカレーションする。Secret漏えいでは再発行後、旧Secretが無効であることとコード・ログから除去されたことを確認する。

## 10. 復旧判定と事後対応

復旧はhealthだけで判断せず、認証・認可、DB、Storage UUID/rw、主要File、Agent、Audit、backup条件を確認する。復旧後は原因、影響、時系列、対応、失敗した防御、再発防止、担当・期限を記録し、手順と監視を更新する。

# テスト品質戦略

**文書状態：設計段階**  
**対象：Mirai AI ワークプラットフォーム Pilot**

## 1. 品質目標

本書は、約10名のPilotで、機能性、データ隔離、セキュリティ、保存の安全性、障害復旧性を検証するための全体戦略を定める。現在の記述は試験方針であり、テスト実行済み・CI構築済みを意味しない。

## 2. 最優先品質リスク

1. 他ユーザー・未所属Projectのデータへアクセスできる。
2. 新規10TB HDD未マウント時にOSルートへ誤書込みする。
3. 単一HDD障害後に別系統バックアップから復元できない。
4. Quota・全体容量保護を迂回し、サービス停止やデータ破損を招く。
5. Agent Sandboxが対象外ファイル、Network、Secretへアクセスする。
6. DeepSeek API障害、遅延、想定外Tool Callを安全に処理できない。

## 3. テストレベル

| レベル | 主目的 | 主な対象 |
|---|---|---|
| 静的検証 | 欠陥の早期発見 | lint、型、依存関係、Secret、構成、文書整合 |
| Unit | 判定ロジック | 認可、Quota、path正規化、状態遷移、マスキング |
| Integration | モジュール境界 | API-DB、File-Storage、Agent-Sandbox、Audit、DeepSeek代替応答 |
| E2E | 利用者業務 | Chat、Work、Project共有、Upload、Artifact、Admin |
| Security | 悪用耐性 | IDOR、Traversal、CSRF、XSS、権限昇格、Sandbox越境 |
| Reliability | 障害時安全性 | HDD切断、read-only、容量閾値、API障害、再起動、復元 |
| Acceptance | Pilot条件 | 10ユーザー、隔離、Quota、監視、監査、バックアップ復元 |

## 4. 自動化方針

- 認可、Quota、パス、Agent状態遷移はUnitで境界値を網羅する。
- 主要APIは成功だけでなく、未認証、権限不足、競合、容量不足、外部障害を自動化する。
- 主要な利用者導線はE2Eの少数精鋭シナリオとする。
- 実機HDD切断、再起動、バックアップ復元等は安全な検証環境で手動または専用手順にする。
- 外部DeepSeek APIは通常CIで実呼出しせず、契約準拠のstubを使い、限定した接続試験を分離する。

## 5. テストデータ

本物の個人情報、機密情報、実Secretをテストへ使用しない。ユーザーとProjectを複数用意し、所有・非所有・Role差を再現する。大容量条件は疎ファイルや容量制限された検証領域など、安全な方法を選び、共有10TB HDDを枯渇させない。

## 6. 品質ゲート

変更を完了候補とする条件は、関連レビュー、必須自動テスト、build、セキュリティ検査が成功し、重大な未解決欠陥がなく、証跡が保存されていることである。未実行、環境都合でblocked、失敗を明確に分ける。CI未通過のmergeは禁止する。

Release段階では新機能を追加せず、重大欠陥、セキュリティ、データ破損、リリース阻害の修正と再検証を優先する。

## 7. 重点的なストレージ品質

- 期待UUIDで `/mnt/storage` がmountされていることを確認する。
- HDD未接続、未マウント、read-only、I/Oエラーで書込みがfail-closedになることを確認する。
- 使用率70/80/85/90/95%の通知・制限を境界値で確認する。
- User/Project Quotaと全体10%以上の運用予備の優先関係を確認する。
- 別媒体または別システムからDB、設定、重要データ、監査情報を復元する。

## 8. 欠陥管理

欠陥は再現条件、期待値、実績、環境、ログ、影響、優先度を記録する。Security、CI停止、データ破損、release blockerをP1、品質低下をP2、改善をP3とする。同一エラーの無限修復を避け、同じ原因が2回続いたら切り分けを見直す。

## 9. 指標

- 必須テスト成功率と未実行数
- 重大度別の未解決欠陥数
- Role・API・状態遷移の要件カバレッジ
- flaky test率、平均修復時間、再発数
- バックアップ成功率と復元試験結果
- Storage警告検知時間、書込み停止までの時間

単一のカバレッジ率だけで品質を判断せず、最重要リスクの検証証跡を優先する。

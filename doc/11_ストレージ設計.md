# Mirai AI ワークプラットフォーム ストレージ設計

**文書状態：設計段階**

## 1. 目的

本書は、Pilotで使用する新規10TB外付けHDDの構成、保存領域、容量制御、監視、障害対応、バックアップを定義する。機器へのフォーマットや既存データ消去は破壊的操作であり、対象確認と人間の承認後に実施する。

## 2. 採用構成

| 項目 | 設計 |
|---|---|
| 物理媒体 | 新規10TB外付けHDD 1台 |
| パーティション | GPT |
| ファイルシステム | ext4 |
| 識別 | ファイルシステムUUID |
| マウント先 | `/mnt/storage` |
| マウント方式 | UUID指定による直接マウント |
| 統合層 | mergerfs不採用 |
| 既存4TB HDD | 初期運用ストレージへ統合しない |
| バックアップ | 別媒体または別システムへ保存 |

メーカー公称10TBは約9.1TiBであり、ext4の管理領域や予約領域により実使用可能容量はさらに小さい。構築後の実測値を容量管理の基準とする。

## 3. マウント安全設計

- `/etc/fstab` はデバイス名ではなくUUIDを指定する。
- アプリケーション起動前にmountpoint、期待UUID、ファイルシステム種別、読書き可否を確認する。
- サービスに `RequiresMountsFor=/mnt/storage` 相当の依存を設ける。
- 未接続、未マウント、読取り専用化、I/O異常時は新規アップロードと成果物生成を停止する。
- マウント失敗時にOSルート上の空ディレクトリへ誤書込みしない。
- 復旧後は自動的に全処理を再開せず、整合性と空き容量を確認する。

`/etc/fstab` の具体的なオプションはLinux環境と障害方針を確認して確定する。起動不能を避ける設定と、未マウント時にアプリケーションを起動しない設定を両立させる。

## 4. ディレクトリ案

```text
/mnt/storage/
├── users/<利用者ID>/workspace/
├── projects/<プロジェクトID>/workspace/
├── artifacts/<年月>/
├── knowledge/<所有者ID>/
├── processing/<実行ID>/
├── temp/<利用者ID>/
└── backups-staging/
```

親はroot管理とし、配下はアプリケーション専用利用者・グループへ最小限の権限を付与する。world-writableを禁止し、`lost+found` を走査しない。利用者へホストパスを直接公開しない。

## 5. ファイル安全

- DBには正規化済み相対パスだけを保存する。
- 絶対パス、`..`、シンボリックリンク脱出を拒否する。
- 表示ファイル名と内部保存名を分け、内部名は一意にする。
- 許可拡張子、MIME、最大サイズを検査する。
- 一時ファイルへ書込み後、サイズとチェックサムを確認して確定する。
- 部分書込みや中断ファイルを成功扱いにしない。

## 6. 容量上限

Pilot初期候補は100GB／利用者、Projectは50、100、500GB等の可変設定とする。所有区分ごとの集計規則を一意にし、保存前に使用量と受信予定量を判定する。並行書込みには容量予約を用いる候補とする。ファイルシステム全体の10%以上を運用予備として確保し、個別上限より全体保護を優先する。

## 7. 警告と制限

| 使用率・状態 | 動作 |
|---|---|
| 70%未満 | 通常運用 |
| 70% | 注意、増加傾向を確認 |
| 80% | 拡張または移行計画を開始 |
| 85% | 管理者警告、上位使用者を精査 |
| 90% | 大容量ジョブ・アップロードを制限 |
| 95% | 緊急保護モード、新規大容量書込みを停止 |
| 未マウント・読取り専用・I/O異常 | 書込み停止、通知、障害手順へ移行 |

しきい値は実使用可能容量を分母とし、監視値とアプリケーション集計値の両方を確認する。

## 8. 監視

- マウント状態、期待UUID、ファイルシステム種別
- 総容量、使用量、空き容量、使用率、増加速度
- inode使用率
- 読取り専用化、ファイルシステムエラー、カーネルI/Oエラー
- USB接続切断・再接続
- USBブリッジ経由で取得可能なS.M.A.R.T.情報と温度
- 上位利用者・Project、孤立ファイル、容量集計差異

S.M.A.R.T.取得不可を正常判定とせず、監視不可として明示する。

## 9. バックアップ

単一の10TB HDDは故障、誤削除、ファイルシステム破損、盗難、筐体障害に対する保護ではない。重要Project、設定、DB、監査情報を別障害系統へ定期保存する。バックアップ先容量、対象、頻度、保持世代、暗号化、アクセス権、RPO、RTO、廃棄方法をPilot開始前に確定する。

バックアップ成功ログだけでなく、定期的な復元試験を行う。既存4TB HDDは10TB全体の完全バックアップとはみなさず、限定用途で再利用する場合も健全性と容量を評価する。

## 10. 障害対応

1. アプリケーション書込みと該当エージェント実行を停止する。
2. UUID、マウント、ケーブル、電源、カーネルログを確認する。
3. 書込みを伴う修復前に影響とバックアップ状態を評価する。
4. ファイルシステム検査はアンマウント等の前提を守り、承認した手順で行う。
5. 復旧後にチェックサム、DB参照、容量集計、主要機能を確認する。
6. 復旧不能時は別系統バックアップから復元する。
7. 原因、データ影響、復旧時刻、再発防止を記録する。

## 11. 既存データの条件付き移行

既存4TB HDDに必要データがある場合のみ、10TB HDDへ初回コピーし、書込みサービス停止後に最終差分を同期する。ファイル件数、総バイト、チェックサムとアプリケーション受入を確認するまで既存媒体を消去しない。必要データがなければ移行工程を省略する。

## 12. 将来拡張

80%到達前に、より大容量媒体への移行、追加ストレージ、RAID・NAS・オブジェクトストレージ等の冗長構成を比較する。初期構成へmergerfsを追加することを既定路線とせず、停止時間、整合性、バックアップ、復元、運用負荷を含めて再設計する。

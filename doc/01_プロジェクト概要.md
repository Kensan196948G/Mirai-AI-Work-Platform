# Mirai AI ワークプラットフォーム プロジェクト概要

**文書状態：実装・検証中（MVPデプロイ済み）**

## 1. 文書の目的

本書は、Mirai AI ワークプラットフォームの背景、目的、対象範囲、関係者、成功条件を共有するための概要文書である。企画書、要件定義書、詳細設計書を上位仕様とし、本書だけで実装完了や運用開始を示すものではない。

## 2. 企画の背景

社内の生成AI利用は、チャット、文書作成、ファイル分析、コーディング、プロジェクト作業などに分散しやすい。単発の回答だけではなく、目標設定から計画、道具の実行、成果物生成、確認までを一つの作業環境で扱い、権限・監査・保存容量を組織的に統制できる基盤が必要である。

## 3. 目的

- Webブラウザから利用できる社内向けAI業務基盤を提供する。
- 会話中心の「Chat」と業務実行中心の「Work」を分ける。
- 利用者別・プロジェクト別の作業領域を安全に分離する。
- AIエージェントの計画、実行、進捗、成果物、履歴を追跡可能にする。
- ストレージ、AI利用、監査、障害を管理者が把握できるようにする。
- Pilotで利用量と効果を測定し、正式運用の判断材料を得る。

## 4. 初期対象範囲

| 項目 | 初期方針 |
|---|---|
| 利用者 | Pilot約10名 |
| 基盤 | Cloudflare Workers + Neon PostgreSQL + React（on-prem Linux 移行は将来） |
| AI | DeepSeek APIを主軸とし、将来の追加を可能にする |
| 主機能 | Chat、Work、Projects、Files、Agents、Tasks、Artifacts、Knowledge、管理 |
| ストレージ | 新規10TB外付けHDD 1台、ext4、UUID指定で `/mnt/storage` へ直接マウント |
| 保護 | 利用者・プロジェクト分離、容量制限、監査、エージェント隔離 |
| Pilot期間 | 3～6か月を目安とする |

## 5. 初期対象外・保留事項

- Entra IDによるシングルサインオン
- OneDriveおよびSharePoint連携
- GitHubおよびMCPの本格連携
- 全社展開時の冗長ストレージ構成
- 本番バックアップ先、頻度、保持世代、暗号化、復旧目標の最終決定

これらは未実装を前提とし、Pilot評価後に別途要件化・承認する。

## 6. 関係者と責務

| 関係者 | 主な責務 |
|---|---|
| Pilot利用者 | 機能利用、問題報告、利用効果の評価 |
| プロジェクト所有者 | メンバー、設定、容量の管理 |
| IT・DX管理者 | 利用者、権限、AI設定、監査、ストレージ、障害対応 |
| 開発・運用担当 | 設計、実装、試験、監視、保守、復旧手順の整備 |
| 情報セキュリティ担当 | 権限、秘密情報、監査、データ持出しの評価 |

## 7. 成功条件

- Pilot利用者が独立した作業領域を継続利用できる。
- Goalから成果物確認までの業務実行が一連で行える。
- 他利用者・他プロジェクトへの不正アクセスを防止できる。
- 管理者が利用量、エージェント実行、障害、監査ログを確認できる。
- 10TB HDDの容量、マウント状態、I/O異常を監視できる。
- 重要データを別系統のバックアップから復元できる。

## 8. Pilotで測定する項目

実使用可能容量、月間増加量、ピーク使用量、利用者平均・最大使用量、プロジェクト容量、AI利用回数、成果物量、一時データ量、API使用量、応答時間、失敗率、バックアップ成否、復元試験結果、利用者満足度、業務時間削減効果を測定候補とする。

## 9. 判断原則

- 単一HDDは冗長化ではない。
- セキュリティ、データ保全、監査可能性を利便性より優先する。
- 未検証の機能を提供済みと扱わない。
- 使用率80%到達前に拡張または移行計画を開始する。
- Pilotの実測値に基づいて正式運用、容量、冗長化、外部連携を再設計する。

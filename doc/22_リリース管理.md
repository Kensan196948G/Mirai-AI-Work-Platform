# リリース管理

**文書状態：設計段階**  
**対象：Mirai AI ワークプラットフォーム**

## 1. 目的

本書は、変更を追跡可能・検証可能・復元可能な単位でPilotへ提供するための管理方針を定める。現時点でGitHub Actions、release workflow、正式な版番号規則が稼働済みであるとは断定しない。

## 2. リリース種別

| 種別 | 内容 | 主な判定 |
|---|---|---|
| Pilot通常版 | 承認済み機能・改善 | 全品質ゲートと受入試験 |
| 修正版 | Pilot中の欠陥修正 | 影響範囲と回帰試験 |
| 緊急修正版 | Security、データ破損、重大停止 | 迅速な承認、最小差分、事後完全検証 |
| 将来版 | 全社展開、SSO、冗長化等 | Pilot実績と別設計 |

## 3. 版管理と成果物

版番号規則を採用する場合、互換性を破る変更、機能追加、修正を区別する。各リリースはcommit SHA、build artifact、checksum、依存関係、DB schema version、設定versionへ一意に対応させる。移動するbranch名や再buildだけをリリース証跡にしない。

## 4. リリース候補の条件

- 受入条件を満たす変更だけが含まれている。
- Review blockerと重大・高Security問題が0件である。
- 必須lint、test、build、security scanが対象commitで成功している。
- 認証・認可、データ隔離、Quota、Storage fail-closed、バックアップ復元が確認されている。
- migration、設定変更、運用・利用者文書、rollback手順が同期している。
- 未実行項目と残存リスクが明示・承認されている。

CI未通過、Security未確認、復元不能の状態でreleaseしない。Release期は新機能を追加しない。

## 5. ストレージ関連の判定

初期構成は新規10TB外付けHDD 1台、ext4、UUID指定の `/mnt/storage` である。既存4TB＋新規4TBやmergerfsを前提とする変更を混入させない。

リリース前に次を確認する。

- 未mount、UUID不一致、read-only、I/Oエラーで書込みが停止する。
- 70/80/85/90/95%の容量動作と10%以上の運用予備が守られる。
- DB・設定・重要データ・監査情報が別系統へバックアップされる。
- 隔離先への復元試験とchecksum照合の証跡がある。

## 6. 承認と職務分離

開発者は変更内容と検証結果を提示し、QAは受入条件、Securityは残存リスク、運用担当は監視・backup・rollback、CTO/Release Managerは最終可否を判断する。同一人物が複数役割を担う小規模Pilotでも、自己承認だけで完結せず別の確認者を設ける。

## 8. 公開後

主要指標、エラー、I/O、容量、Agent滞留、DeepSeek API失敗率を監視する。重大事象があれば受付停止、rollback、障害対応を判断する。安定確認後にIssue、Project、state、文書へ実績を反映するが、未確認結果を成功として記録しない。

## 9. 緊急修正版

緊急時もSecret変更、deploy、push、merge、release等の権限境界は維持する。差分を最小化し、最低限のSecurity・回帰・rollback確認を行う。省略した検証は公開後に期限と担当を定めて実施する。

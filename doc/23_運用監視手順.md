# 運用監視手順

**文書状態：設計段階**  
**対象：Mirai AI ワークプラットフォーム Pilot運用**

## 1. 目的

本書は、Pilot運用中の異常を早期に検知し、安全な停止・復旧判断へつなげる監視手順案を定める。監視製品、閾値の継続時間、通知先、当番体制は未確定である。

## 2. 監視対象

| 分類 | 指標・状態 | 主な対応 |
|---|---|---|
| Service | health、応答時間、5xx、再起動 | 影響確認、ログ相関、必要なら受付停止 |
| Auth | login失敗、拒否急増、Role変更 | 攻撃・設定不良・アカウント問題を切分け |
| Agent | 待ち数、失敗率、実行時間、資源使用 | 上限、外部API、Sandboxを確認 |
| DeepSeek | timeout、429/5xx、利用量 | 再試行抑制、利用者通知、費用・上限確認 |
| DB | 接続、容量、遅延、backup | 書込み整合性と復旧可否を確認 |
| Storage | mount、UUID、read-only、I/O、容量、inode | 異常時は書込み停止し障害手順へ移行 |
| Audit | ログ流量、欠落、時刻、転送 | 証跡欠落の影響を評価 |
| Backup | 成否、世代、容量、復元試験日 | 失敗を放置せず再実行・原因確認 |

## 3. 10TB HDD監視

新規10TB HDDは単一障害点であるため、次を重点監視する。

- `/mnt/storage` がmountpointかつ期待UUIDのext4であること
- read-write状態、空き容量、使用率、inode
- カーネルのUSB切断、filesystem、I/Oエラー
- 取得可能な場合はS.M.A.R.T.のoverall status、reallocated/pending sector、温度
- 書込みテストは専用probeへ限定し、既存データを変更しない

| 状態 | 運用動作 |
|---|---|
| 70% | 注意。増加率と不要Tempを確認 |
| 80% | 移行・追加・冗長化計画を開始 |
| 85% | 管理者へ警告し、増加要因と日数予測を確認 |
| 90% | 大容量Job・Uploadを制限 |
| 95% | 緊急保護モード。重要書込み以外を停止 |
| 未mount／UUID不一致／read-only／I/Oエラー | 新規書込みを停止し、障害対応へ移行 |

個別User/Project Quotaに余裕があっても、全体保護を優先する。OSルートの同名ディレクトリへフォールバックしない。

## 4. 監視頻度案

| 頻度 | 内容 |
|---|---|
| 常時または短間隔 | service health、mount、I/O、容量閾値、5xx、Agent失敗 |
| 日次 | Backup成否、容量増加、異常ログ、Job滞留、DeepSeek利用量 |
| 週次 | Quota、利用傾向、監査拒否、S.M.A.R.T.傾向、通知テスト |
| 月次 | 復元試験または計画確認、権限棚卸し、容量枯渇予測、Runbook更新 |

実際のRPO/RTOと運用体制に合わせて確定する。

## 5. アラート処理

1. 受信時刻、アラートID、対象、値を記録する。
2. Request ID、service log、audit、kernel logを相関する。
3. 利用者影響、データ破損、Security、継続悪化の有無で重大度を決める。
4. 書込み継続が危険な場合はfail-closedを維持する。
5. 担当へ通知し、暫定対応、復旧判定、事後対応を記録する。

アラートを単に無効化して解決扱いにしない。閾値変更は根拠と承認を残す。

## 6. バックアップ監視

10TB HDDと別故障ドメインの保存先について、Job成功だけでなく対象件数、容量、checksum、世代、暗号化、保存先残容量を確認する。定期的に隔離先へ復元し、DB・設定・重要Project・監査情報を利用可能か検証する。


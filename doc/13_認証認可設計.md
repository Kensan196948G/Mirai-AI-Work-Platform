# 認証認可設計

**文書状態：設計段階**  
**対象：Mirai AI ワークプラットフォーム Pilot**

## 1. 目的

本書は、約10名のPilot利用者が、本人に許可されたユーザー領域・Project・管理機能だけを利用できるようにする認証・認可方針を定義する。SSO方式は保留事項であり、本書は特定製品の導入完了を示さない。

## 2. 基本原則

- すべての非公開画面とAPIで認証を必須とする。
- 認可は画面表示だけでなく、APIとファイルアクセスの直前にサーバー側で判定する。
- 最小権限、明示許可、既定拒否を採用する。
- ユーザー入力の所有者ID・Role・保存先を信頼せず、認証済み主体とDBの所属情報から決定する。
- 管理者操作、権限変更、認証失敗を監査対象とする。

## 3. 主体とRole

| Role | 主な権限 | 禁止事項 |
|---|---|---|
| Pilot User | 個人Workspace、所属Project、Chat、Work、Filesの利用 | 他ユーザー領域、未所属Project、管理機能へのアクセス |
| Project Owner | 上記に加え、担当Projectの設定、メンバー、Quota管理 | 他Projectの管理、全体設定変更 |
| IT/DX Admin | ユーザー、Project、Role、Quota、監査ログ、システム状態の管理 | 通常業務データの目的外閲覧、監査証跡を残さない操作 |
| Service Account | 定義済みサービス間処理 | 対話ログイン、用途外API、不要なファイル領域 |

同一利用者が複数Roleを持つ場合も、対象Projectと操作単位で権限を評価する。Admin権限の常用は避ける。

## 4. 認証設計

1. クライアントはHTTPS経由で認証を開始する。
2. 認証成功後、推測困難なセッション識別子を発行する。
3. Cookieを用いる場合は `Secure`、`HttpOnly`、適切な `SameSite` を設定する。
4. ログアウト、無効化、パスワード変更、重大な権限変更時に既存セッションを失効させる。
5. アイドル時間と絶対有効期間をPilot開始前に決め、期限切れ後は再認証する。
6. ログイン失敗をレート制限し、識別子の存在を推測しにくい応答とする。

ローカル認証を採用する場合は、パスワードを十分に強い一方向ハッシュで保存し、平文・復号可能形式で保持しない。Entra ID等のSSOは将来候補であり、採用時はOIDCのissuer、audience、署名、nonce/state、時刻を検証する。

## 5. 認可判定

| リソース | 判定キー | 許可条件 |
|---|---|---|
| User File | `owner_type`、`owner_id` | 認証主体本人か、明示された管理権限がある |
| Project | `project_members` | 有効なメンバーで、操作に必要なProject Roleを持つ |
| Agent Run | `user_id`、`project_id` | 実行者本人か対象Projectの許可されたメンバー |
| Artifact | 関連 `agent_run` と `file_id` | 元の実行・保存先の両方にアクセス可能 |
| Admin API | システムRole | IT/DX Adminであり、必要なら再認証済み |

ファイルパスから認可を推測せず、DB上の所有関係を先に確認する。`/mnt/storage` 全体をユーザーまたはAgent Containerへ公開せず、許可されたWorkspaceだけをbind mountする。

## 6. 権限変更とライフサイクル

- アカウント作成、停止、再有効化、Role変更は承認者と理由を記録する。
- Project脱退・アカウント停止後は新規アクセスを即時拒否し、既存セッションも失効対象とする。
- Project Owner不在を避けるため、Owner移管を完了してから旧Ownerを削除する。
- Service Accountの資格情報はSecret管理し、期限・用途・所有者を登録する。
- 定期棚卸しで休眠アカウント、過剰権限、孤立Projectを確認する。

## 7. 失敗時の動作

認証基盤や認可情報を確認できない場合はアクセスを拒否する。新規10TB HDDが未接続、未マウント、read-only、またはI/Oエラーの場合は、認証済み利用者であってもUpload、Artifact生成、ファイル更新を停止し、OSルート側へ代替保存しない。

## 8. 検証観点

- 未認証、期限切れ、改ざん済みセッションが拒否される。
- User AがUser BのIDやパスを指定しても参照・変更できない。
- Project Roleごとの許可・拒否がAPI単位で一致する。
- Role変更とアカウント停止が既存セッションへ反映される。
- 管理操作と認証失敗にRequest ID付き監査ログが残る。
- UIで非表示の操作もAPI直接呼出しでは拒否される。

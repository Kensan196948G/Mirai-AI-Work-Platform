# Mirai AI ワークプラットフォーム 機能仕様

**文書状態：設計段階**

## 1. 目的

本書は、Pilotで実現を検討する機能、主要な入出力、権限制御、異常時動作を整理する。受入試験を通過するまでは実装済みと扱わない。

## 2. 利用者区分

| 区分 | 主な権限 |
|---|---|
| Pilot利用者 | 自分のWorkspace、Chat、Work、Files、参加プロジェクトの利用 |
| プロジェクト所有者 | プロジェクト設定、メンバー、役割、容量の申請・管理 |
| IT・DX管理者 | 利用者、全プロジェクト、容量、AI設定、監査、システム状態の管理 |

権限はサーバー側で判定し、画面を隠すだけで制御したことにしない。

## 3. Chat

### 3.1 機能

- 会話の作成、題名変更、一覧、参照
- DeepSeek APIとの対話
- プロジェクト文脈の選択
- 許可されたファイルの添付
- 応答モデルと利用量の記録

### 3.2 異常時

AI提供者のタイムアウトや上限超過時は、入力内容を失わず再試行可能な状態を示す。機密情報や秘密情報をエラーへ出力しない。

## 4. Work

### 4.1 基本フロー

```text
Goal入力 → Plan生成 → 利用者確認 → Task実行
→ Tool結果検証 → Artifact生成 → Review → 採用または再実行
```

### 4.2 機能

- 目標、制約、成果物形式の入力
- 計画とタスク順序の表示・修正
- 実行開始、中止、再実行
- 進捗、現在処理、エラー、開始・終了時刻の表示
- 成果物と実行履歴の関連付け
- 元に戻しにくい操作に対する人の確認

## 5. Projects

- プロジェクトの作成、表示、編集、終了、削除申請
- 所有者、メンバー、役割の管理
- Workspace、Files、Knowledge、Artifactsの集約
- プロジェクト単位の容量上限と使用量表示
- 他プロジェクトからのアクセス拒否

## 6. Files

- 一覧、検索、アップロード、取得、移動、削除
- サイズ、所有者、プロジェクト、種別、作成・更新日時、チェックサムの記録
- Office、PDF、テキスト、画像等の許可種別管理
- ファイル名と内部保存名の分離
- 最大サイズ、許可拡張子、MIME整合性の検査
- `..`、絶対パス、シンボリックリンク脱出の拒否
- 容量不足、未マウント、読取り専用、I/O異常時の書込み拒否

## 7. Agents

- 実行の作成、開始、中止、状態確認、履歴参照
- Plan、Task、Tool、Artifactの関係管理
- 実行ごとのSandboxと資源上限
- 許可されたFile、Shell、Network等の道具の実行
- 対象Workspaceだけのマウント
- エラー、開始・終了、AIモデル、利用量の記録

## 8. Artifacts

- HTML、Markdown、PDF、Office文書等の成果物保存
- 利用者・プロジェクト・エージェント実行との関連付け
- 生成日時、種別、作成元、チェックサムの表示
- Review結果、採用状態、再生成履歴の管理候補

## 9. Knowledge

プロジェクト内の参照情報を登録・整理し、ChatやWorkで利用する機能を将来拡張可能にする。RAG、索引方式、更新検知、引用表示、アクセス権の詳細は別途設計し、初期提供範囲を受入前に確定する。

## 10. Admin

- 利用者、状態、役割、容量上限の管理
- プロジェクト、所有者、使用量の管理
- AI提供者、モデル、利用制限の設定
- ストレージ使用率、マウント、I/O、取得可能な健全性情報の表示
- エージェント実行状況と失敗の確認
- 監査ログの検索と出力
- 全体保護モードと利用者通知

## 11. 容量制御

保存先は、新規10TB外付けHDD 1台をext4で構成し、UUID指定で `/mnt/storage` へ直接マウントする初期構成を前提とする。mergerfsは使用せず、重要データは別系統へバックアップする。保存前に「現在使用量＋受信予定サイズ」が利用者上限、プロジェクト上限、全体保護上限を超えないことを確認する。全体の安全制限を最優先とする。並行書込みによる超過を防ぐため、予約または原子的な判定方式を実装時に選定する。

## 12. 通知

容量警告、エージェント完了・失敗、ストレージ障害、管理者による停止、バックアップ失敗を通知候補とする。画面内通知を初期候補とし、電子メール等の外部通知は連携要件確定後に追加する。

## 13. 共通異常処理

- 利用者向けメッセージと内部ログを分離する。
- エラーには追跡用の要求IDまたは実行IDを付ける。
- 再試行可能か、管理者対応が必要かを示す。
- 部分保存を検知し、完了扱いにしない。
- 監査対象操作の失敗も記録する。

## 14. 受入観点

機能ごとに正常系、権限拒否、入力境界、容量超過、AI障害、ストレージ障害、並行操作、監査記録、アクセシビリティを検証する。静的な画面表示だけを機能完成と数えない。

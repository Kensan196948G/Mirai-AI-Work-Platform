# 性能・容量計画

**文書状態：設計段階**

## 1. 対象と前提

初期対象は約10名のPilot Userである。ストレージは新規10TB外付けHDD 1台（約9.1TiB、ext4、`/mnt/storage`）であり、USB接続と単一回転媒体の性能・可用性制約を前提とする。

## 2. 測定対象

| 分類 | 指標 |
|---|---|
| Web/API | 応答時間、エラー率、同時接続数、リクエスト数 |
| Agent | 待ち時間、実行時間、同時実行数、失敗率、CPU・メモリ |
| ストレージ | 読書きレイテンシ、スループット、IOPS、キュー、I/Oエラー、使用率 |
| データ | User/Project別容量、月間増加量、Artifacts量、Temp量 |
| 外部API | DeepSeek API応答時間、Rate Limit、失敗率、利用量 |
| 運用 | バックアップ時間、復元時間、監視遅延 |

## 3. 性能目標

10名Pilotで通常利用に支障のない応答性を求めるが、数値SLO、同時Agent上限、最大Uploadサイズ、バッチ実行時間は**未決**である。Pilot開始前に代表シナリオと暫定基準を設定し、実測により改定する。

## 4. 負荷シナリオ

- 10名の同時ログイン、Chat、ファイル一覧、Project共有
- 複数Agentの同時実行とArtifacts生成
- 大容量Upload/Downloadとバックアップの競合
- Quota境界、使用率70/80/85/90/95%付近の処理
- 外部API遅延・失敗、HDD未マウント・read-only時の縮退

## 5. 容量予測

構築後の実使用可能容量を基準に、最低10%を運用予備として除外する。日次・月次増加量から80%到達日を予測し、調達、コピー、照合、受入試験に必要なリードタイムを確保する。既存4TBデータを移行する場合は、その実測容量を初期使用量へ加える。

## 6. 制御方針

- User/Project Quota、Upload上限、Agent同時実行数を管理者が調整できるようにする。
- 90%で大容量Job/Uploadを制限し、95%で緊急保護する。
- バックアップと大容量処理は時間帯を分離する候補とする。
- Temp/Cacheは24時間～7日の範囲で自動削除可能とする。正式値は**未決**である。

## 7. 見直し

Pilot中は月次を候補として性能・容量レビューを実施する。しきい値超過、ユーザー増加、大型Project、ストレージ方式変更の前後では臨時レビューを行う。

# Mirai AI ワークプラットフォーム データ設計

**文書状態：設計段階**

## 1. 目的

本書は、業務メタデータ、ファイル実体、AI実行情報、監査情報の論理モデルと整合性方針を定義する。物理DB製品、列型、索引、移行方式は実装前に確定する。

## 2. データ分類

| 分類 | 例 | 主な保存先 |
|---|---|---|
| 識別・権限 | 利用者、役割、Projectメンバー | データベース |
| 業務メタデータ | 会話、Work、Task、Agent実行 | データベース |
| ファイルメタデータ | 相対パス、サイズ、種別、チェックサム | データベース |
| ファイル実体 | 添付、Knowledge、Artifact | `/mnt/storage` |
| 一時処理データ | 変換中ファイル、キャッシュ | `/mnt/storage/processing` 等 |
| 監査情報 | 誰が、いつ、何を、結果 | 改変制限したログまたはデータベース |
| 秘密情報 | AI APIキー、接続資格情報 | Secret管理基盤 |

秘密情報を一般テーブルやファイル実体へ平文保存しない。

## 3. 論理エンティティ

| エンティティ | 主な属性 |
|---|---|
| users | id、login_id、display_name、role、storage_quota_bytes、status |
| projects | id、name、owner_id、storage_quota_bytes、status |
| project_members | project_id、user_id、role |
| files | id、owner_type、owner_id、relative_path、size_bytes、mime_type、checksum |
| conversations | id、user_id、project_id、title |
| messages | id、conversation_id、role、content、model、token_usage |
| works | id、user_id、project_id、goal、status、version |
| agent_runs | id、work_id、user_id、project_id、goal、status、started_at、finished_at |
| tasks | id、agent_run_id、title、status、sequence |
| artifacts | id、agent_run_id、file_id、artifact_type、review_status |
| audit_logs | id、user_id、action、resource_type、resource_id、result、ip、created_at |

`works` は上位仕様のWork概念を明確化する追加候補であり、実装時に `agent_runs` との責務を確定する。

## 4. 主要な関係

```text
User ──< ProjectMember >── Project
User ──< Conversation ──< Message
User/Project ──< File
User/Project ──< Work ──< AgentRun ──< Task
AgentRun ──< Artifact >── File
User ──< AuditLog
```

所有範囲を示す外部キーと認可判定を一貫させ、孤立データを作らない。

## 5. 識別子と時刻

外部公開する識別子は推測困難な値を候補とし、表示名やファイル名を識別子にしない。全レコードに必要に応じて作成日時、更新日時、作成者、更新者、バージョンを持たせる。保存時刻はUTC、表示時にAsia/Tokyo等へ変換する。

## 6. ファイルパス

DBには `/mnt/storage` を含む絶対パスではなく、管理対象ルートからの正規化済み相対パスを保存する。利用者入力の `..`、絶対パス、区切り文字の不正利用を拒否する。シンボリックリンクによる管理範囲外への脱出を防ぐ。

## 7. 整合性

- ファイルメタデータ確定前にファイル実体の書込み完了を検証する。
- 一時名で書込み、検証後に原子的な名前変更を行う候補とする。
- サイズとチェックサムを保持し、破損・重複・移行照合に利用する。
- Project所有者とメンバー関係へ外部キーまたは同等の制約を設ける。
- Taskの順序、AgentRunの状態遷移に不正な組合せを許さない。
- 削除時のDBとファイル実体の順序、再試行、孤立回収を設計する。

## 8. 容量集計

利用者所有とProject所有の二重計上を避け、ファイルごとに一つの課金先を決める。書込み受付時に容量を予約し、完了で確定、失敗で解放する方式を候補とする。論理使用量とファイルシステム実使用量の差異を定期照合し、差異原因を記録する。

## 9. 状態管理

Work、AgentRun、Task、File処理には許可された状態遷移を定義する。例として、実行は受付、計画中、確認待ち、実行中、成功、失敗、中止を持つ。成功後に実行中へ戻す等の不正遷移を拒否し、再実行は新しい実行記録として関連付ける。

## 10. 保持と削除

- 利用者・Project本体データは明示削除まで保持する初期案とする。
- 一時データは24時間～7日を候補として自動削除する。
- 処理データは完了・失敗後の調査期間を経て削除する。
- 監査ログはPilot中原則保持し、正式運用前に期間を確定する。
- 論理削除、物理削除、バックアップ上の保持を区別する。
- 法令、契約、情報分類による保持要件を別途確認する。

## 11. バックアップと復元

データベースとファイル実体の整合する時点を復元できるようにする。10TB HDDとは別の媒体または別システムへ保存し、暗号化、保持世代、RPO、RTOを確定する。復元試験では件数、容量、チェックサム、参照関係、権限、アプリケーション表示を確認する。

## 12. 移行

既存4TB HDDに移行対象がある場合のみ、初回コピー、書込み停止、最終差分、件数・総バイト・チェックサム照合、受入確認を行う。完了まで既存HDDを消去せず、読取り専用のロールバック元として保管する。移行対象がない場合は実施しない。

# Mirai AI ワークプラットフォーム インターフェース仕様

**文書状態：設計段階**

## 1. 目的

本書は、ブラウザ、アプリケーションAPI、内部サービス、AI提供者、ファイルストレージの境界を定義する。経路名や形式は設計候補であり、OpenAPI等の機械可読仕様と実装試験によって確定する。

## 2. 共通API方針

- 通信はHTTPSを前提とする。
- APIのバージョンを経路に含める候補は `/api/v1` とする。
- 認証済み利用者と役割をサーバー側で検証する。
- 要求ごとに要求IDを発行または受け入れ、応答とログへ含める。
- 時刻はISO 8601形式のUTCを基本とし、画面で利用者の時間帯へ変換する。
- 識別子は推測困難な値を使用する候補とする。
- 一覧はページング、並べ替え、許可された絞込みを備える。
- 入力上限、許可値、文字コード、MIMEを明示する。

## 3. 応答形式案

成功応答は対象データと必要なメタデータを返す。失敗応答は次の構造を候補とする。

```json
{
  "error": {
    "code": "STORAGE_READ_ONLY",
    "message": "現在は新しいファイルを保存できません。",
    "request_id": "要求識別子",
    "retryable": false
  }
}
```

`message` は秘密情報や内部パスを含めない。内部診断情報は要求IDでログと対応付ける。

## 4. 主要な外部向け資源

| 資源 | 操作例 | 主な制御 |
|---|---|---|
| conversations | 作成、一覧、参照、題名変更 | 所有者・Project権限 |
| messages | 送信、一覧 | 文脈権限、入力上限、AI流量制御 |
| works | 作成、開始、中止、再実行、参照 | 所有者、危険操作確認 |
| tasks | 一覧、参照 | 親Workへの参照権限 |
| projects | 作成、参照、更新、終了 | 所有者・管理者権限 |
| project-members | 追加、役割変更、削除 | 所有者権限、自己ロックアウト防止 |
| files | 一覧、アップロード、取得、移動、削除 | 所有範囲、種別、容量、パス検証 |
| agent-runs | 作成、開始、中止、状態参照 | Sandboxプロファイル、資源上限 |
| artifacts | 一覧、参照、取得、確認 | 元Workと保存先の権限 |
| audit-logs | 検索、出力 | 管理者限定、出力監査 |
| storage-status | 状態参照 | 管理者向け詳細、一般向け要約 |

## 5. ファイル転送

アップロード開始前に予定サイズ、保存先、所有種別を検証する。大容量ファイルは分割アップロードを候補とするが、未完成データを公開領域へ置かない。完了後にサイズ、MIME、チェックサムを確認し、メタデータを確定する。取得時は権限を再検証し、利用者から絶対パスを受け取らない。

## 6. 非同期処理

Work、エージェント実行、大容量ファイル処理は非同期を基本とする。受付応答は実行IDと状態参照先を返す。状態候補は `queued`、`planning`、`awaiting_review`、`running`、`succeeded`、`failed`、`cancelled` とする。画面更新はポーリング、サーバー送信イベント、WebSocket等から実装時に選定する。

## 7. DeepSeek API連携

- AI提供者固有の形式をProvider層で吸収する。
- System Prompt、Project Context、User Request、Tool結果を分離する。
- APIキーはSecretから読み込み、要求・ログ・DBへ平文保存しない。
- 接続・読取りタイムアウト、再試行上限、流量制限を設ける。
- Tool Callは内容と権限を検証してから実行する。
- モデル、利用量、遅延、結果、エラーを追跡可能にする。
- AI提供者へ送信可能なデータ区分を運用方針で定める。

## 8. ストレージサービス境界

アプリケーションはファイル保存前に、マウント済み、期待UUID、読書き可能、空き容量、利用者上限、Project上限、全体保護状態を問い合わせる。書込み先は `/mnt/storage` 配下に限定し、mergerfsや複数マウント先の選択機能を初期仕様に含めない。

## 9. 監査イベント境界

認証、ファイル、Project、Work、Agent、管理設定、容量変更は、成功・失敗を含む構造化イベントとして監査サービスへ渡す。監査記録失敗時に対象操作を続けるか停止するかは、操作の重要度別に定義する。

## 10. 冪等性と競合

再送され得る作成・開始操作には冪等キーの採用を検討する。更新にはバージョン番号または更新時刻を用いた競合検知を設ける。容量予約は並行アップロードで上限を超えないよう原子的に扱う。

## 11. 互換性と変更管理

破壊的変更はAPIバージョンを分け、廃止予定を事前通知する。OpenAPI、応答例、エラーコード、権限表、結合試験を同時に更新する。実装と文書の差異をリリース前に機械的またはレビューで確認する。

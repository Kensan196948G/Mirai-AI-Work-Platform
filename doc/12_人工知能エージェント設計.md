# Mirai AI ワークプラットフォーム 人工知能エージェント設計

**文書状態：設計段階**

## 1. 目的

本書は、AIエージェントがGoalからPlan、Task、Tool、Artifact、Reviewを扱うための責務、状態、隔離、承認、監査を定義する。自律実行の安全性を優先し、実装・検証前に自動実行可能とみなさない。

## 2. 基本フロー

```text
利用者がGoalを入力
  → 文脈と権限を確認
  → Planを生成
  → 利用者が範囲を確認
  → Taskへ分解
  → Sandboxを起動
  → 許可されたToolを実行
  → 結果を検証
  → Artifactを生成
  → 利用者がReview
  → 採用・再実行・中止
```

## 3. 構成要素

| 要素 | 責務 |
|---|---|
| Goal受付 | 目的、制約、成果物、保存先の取得 |
| Planner | 実行可能なPlanとTaskへの分解 |
| Policy判定 | 利用者権限、Project、道具、データ区分、危険度の確認 |
| Executor | Task順序、再試行、中止、タイムアウトの制御 |
| Sandbox管理 | 一時コンテナ、資源上限、マウント、ネットワークの隔離 |
| Tool仲介 | File、Shell、Network等の入力検証と結果制限 |
| Artifact管理 | 成果物保存、メタデータ、生成元、チェックサム |
| Review管理 | 人の確認、採用、却下、再実行の記録 |
| Audit連携 | Goal、Plan、Tool、結果、状態、承認の記録 |

## 4. 状態モデル案

| 状態 | 意味 |
|---|---|
| queued | 実行待ち |
| planning | Plan生成中 |
| awaiting_review | 利用者確認待ち |
| running | Task実行中 |
| succeeded | 正常終了し成果を確定 |
| failed | 回復不能または上限到達 |
| cancelled | 利用者または管理者が中止 |

状態遷移はサーバー側で制約し、再実行は元記録を書き換えず新しい実行として関連付ける。

## 5. AI提供者

初期はDeepSeek APIを主軸とする。Provider層でモデル固有APIを抽象化し、将来の他LLM追加を可能にする。System Prompt、Project Context、User Request、Tool結果を分離し、送信対象データを権限と情報区分で制御する。APIキーはSecretとして管理し、ログやDBへ平文保存しない。

## 6. Sandbox

- エージェント実行ごとに一時コンテナを起動する候補とする。
- 対象利用者または対象ProjectのWorkspaceだけを `/workspace` へバインドマウントする。
- ホストの `/mnt/storage` 全体や他利用者領域を公開しない。
- 既定は非特権利用者、読取り専用ルート、必要最小限の書込み領域とする。
- CPU、メモリ、実行時間、プロセス数、出力サイズを制限する。
- ネットワークは既定拒否を候補とし、必要な宛先だけを許可する。
- 終了時に一時資格情報と不要な一時領域を破棄する。

## 7. Tool設計

| Tool | 主な制御 |
|---|---|
| File | 管理ルート内の相対パス、所有者権限、種別、容量 |
| Shell | 許可コマンド、引数検証、非特権、時間・出力量上限 |
| Network | 許可宛先、方式、応答サイズ、秘密情報の送信禁止 |
| Search | 対象Project、結果件数、引用元の記録 |
| Artifact | 許可形式、保存先、チェックサム、容量予約 |

LLMが生成したTool Callをそのまま信用せず、構造検証、権限判定、危険度判定後に実行する。Tool結果もサイズと機密性を確認してからAIへ戻す。

## 8. 人の承認境界

次の操作は原則として明示確認または管理者承認を必要とする。

- ファイル・Project・利用者データの削除
- 外部への送信、公開、共有範囲の拡大
- 権限、メンバー、容量上限、システム設定の変更
- 新しい秘密情報の登録・更新
- 破壊的なShell操作、永続サービスの変更
- 高額または大量のAI・計算資源利用
- バックアップ削除、復元、本番相当環境への反映

確認画面には具体的な対象、影響、取消可否を表示する。

## 9. 文脈管理

利用者の指示、Project情報、選択ファイル、過去会話を目的に必要な範囲だけ組み立てる。他Projectのデータ、不要な個人情報、APIキーを含めない。長い文脈は要約や選択を行うが、重要な制約を失わないよう元情報との対応を記録する。

## 10. 成果物

Artifactは、元のWork、AgentRun、Task、入力資料、モデル、生成日時、保存先、種別、チェックサム、Review状態へ関連付ける。生成完了と業務採用を区別し、人が内容、権利、機密性、形式を確認してから採用する。

## 11. 失敗と再試行

- AI提供者、Tool、ストレージ、権限、入力不備を別のエラー種別にする。
- 再試行可能性と待機時間を定義する。
- 同じ副作用操作を重複実行しないよう冪等性を設ける。
- 上限回数を超えたら停止し、原因と部分成果を示す。
- ストレージは新規10TB外付けHDD 1台をext4で構成し、UUID指定で `/mnt/storage` へ直接マウントする初期構成を前提とする。mergerfsは使用せず、別系統バックアップで保護する。
- ストレージ未マウント、読取り専用、I/O異常時は成果物書込みを開始しない。
- 中止時に進行中プロセス、一時ファイル、容量予約を回収する。

## 12. 監査と可観測性

Goal、Plan版、Task、Tool名、対象、開始・終了、結果、モデル、トークン利用量、資源利用、Artifact、承認者を記録する。入力本文やTool結果の全文記録は機密性と最小化の要件を評価し、必要範囲に限定する。要求ID、Work ID、AgentRun IDでログを相関する。

## 13. 品質・安全評価

- 他利用者・他Projectへのアクセス拒否
- Prompt Injectionと不正Tool Callへの耐性
- パストラバーサル、シンボリックリンク脱出の防止
- 危険操作の承認回避ができないこと
- タイムアウト、資源上限、出力上限
- AI障害、ストレージ障害、中止、再試行時の整合性
- 成果物の追跡性とReview記録
- 秘密情報が画面、ログ、AI送信へ漏れないこと

## 14. 将来拡張

複数モデル選択、役割別エージェント、RAG、MCP、GitHub連携、承認フロー、定期タスクを候補とする。追加時は権限、監査、送信先、費用、停止方法、障害影響を個別に設計する。

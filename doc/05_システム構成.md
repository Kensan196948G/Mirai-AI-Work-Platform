# Mirai AI ワークプラットフォーム システム構成

**文書状態：設計段階**

## 1. 目的

本書は、Pilot向けシステムの論理構成、責務境界、主要な通信と障害境界を示す。製品や配置は候補を含み、構築済みであることを示さない。

## 2. 論理構成

```text
利用者ブラウザ
  ↓ HTTPS
Webフロントエンド
  ↓ アプリケーションAPI
APIゲートウェイ
  ├── 認証・認可
  ├── プロジェクトサービス
  ├── ファイルサービス
  ├── エージェントサービス
  ├── ストレージサービス
  └── 監査サービス
       ├── メタデータ用データベース
       ├── エージェント実行環境
       ├── DeepSeek API
       └── /mnt/storage
              ↓ UUID指定の直接マウント
          新規10TB外付けHDD 1台（ext4）

別媒体・別システム ← 定期バックアップ／復元試験
```

## 3. 構成要素

| 要素 | 責務 |
|---|---|
| Webフロントエンド | Chat、Work、Projects、Files、Agents、Adminの画面提供 |
| APIゲートウェイ | 認証、認可、要求ID、流量制御、経路制御 |
| プロジェクトサービス | プロジェクト、メンバー、役割、容量上限 |
| ファイルサービス | アップロード、取得、移動、削除、メタデータ、検査連携 |
| エージェントサービス | Plan、Task、Sandbox、道具実行、状態、成果物 |
| ストレージサービス | 使用量、容量判定、マウント・I/O監視、保護制御 |
| 監査サービス | 操作イベントの記録、検索、相関 |
| データベース | 利用者、プロジェクト、会話、実行、ファイル索引、監査情報 |
| ファイルストレージ | 実体ファイル、成果物、知識、一時処理データ |
| AI提供者 | DeepSeek APIによるモデル推論 |

## 4. 配置方針

初期Pilotは単一Linux基盤を候補とするが、アプリケーション、データベース、エージェント実行、バックアップを論理的に分離する。エージェントは実行ごとの一時コンテナを基本とし、対象利用者または対象プロジェクトのWorkspaceだけを `/workspace` へバインドマウントする。ホストの `/mnt/storage` 全体は公開しない。

## 5. ストレージ構成

- 新規10TB外付けHDD 1台をGPT、ext4で構成する。
- UUIDを `/etc/fstab` に登録し、`/mnt/storage` へ直接マウントする。
- mergerfsは採用しない。
- 既存4TB HDDと新規4TB HDDを組み合わせる案は採用しない。
- アプリケーションは `/mnt/storage` だけを保存ルートとして扱う。
- サービス起動はマウント済み、期待UUID、読書き可能を前提とする。
- 未マウント時にOSルート側の同名ディレクトリへ誤書込みしない。
- 別媒体または別システムへのバックアップを必須とする。

## 6. 信頼境界

| 境界 | 必要な制御 |
|---|---|
| ブラウザとAPI | HTTPS、認証、セッション保護、入力検証、流量制御 |
| APIとデータベース | 最小権限の接続情報、暗号化、問い合わせ制御 |
| APIとファイル領域 | 相対パス、所有者検証、パストラバーサル防止 |
| エージェントとホスト | コンテナ隔離、資源上限、道具権限、限定マウント |
| システムとAI提供者 | 秘密情報管理、送信データ制御、障害時処理 |
| 主ストレージとバックアップ | 別障害系統、暗号化、保管権限、復元検証 |

## 7. 起動依存関係

```text
10TB HDD接続
  → UUID一致とext4確認
  → /mnt/storageマウント
  → 読書き・空き容量確認
  → データベースおよび依存サービス確認
  → アプリケーション起動
  → エージェント実行受付開始
```

ストレージ確認に失敗した場合、読取り可能な管理画面や障害表示の提供可否を別途設計するが、新規アップロードと成果物生成は開始しない。

## 8. 可観測性

アプリケーションログ、アクセスログ、エージェントログ、ストレージログ、監査ログ、AI利用ログを区別し、要求ID・実行IDで相関可能にする。容量、空き容量、マウント、I/O、API失敗率、実行待ち時間、資源使用量を監視候補とする。

## 9. 将来拡張

複数LLM、SSO、Microsoft 365、GitHub、MCP、RAG、部門別Knowledge、承認フロー、定期実行を段階追加できる境界を保つ。ストレージ拡張はPilot実測後に移行または冗長構成として再設計し、単純なディスク追加を前提にしない。

2. Linuxストレージ設計

2.1 Mount

新規10TB外付けHDD（公称10TB≒約9.1TiB、GPT / ext4）
  ↓ UUID指定
/mnt/storage

新規10TB HDDはUUID指定で/etc/fstabに登録し、デバイス名変動の影響を避ける。10TBはメーカー公称容量であり、Linux上の表示容量とext4フォーマット後の実使用可能容量が小さくなることを前提とする。既存4TB HDDはこのマウント構成へ含めない。

2.2 マウント安全設計

アプリケーションは必ず/mnt/storageのみを参照する。systemdサービスにRequiresMountsFor=/mnt/storage相当の依存関係を設定し、起動時にmountpoint、期待するUUID、書込み可否を検証する。HDDの未接続、切断、read-only化、I/Oエラーを検知した場合は新規UploadとArtifact生成を停止し、OSルートファイルシステム上の同名ディレクトリへ誤書込みしない。

/mnt/storageの親ディレクトリはroot管理とし、配下はアプリケーション専用ユーザー／グループへ必要最小限の権限を付与する。world-writableを禁止し、ext4のlost+foundはアプリケーションの走査対象外とする。

2.4 既存データの条件付き移行

既存4TB HDDに移行対象データがある場合は、10TB HDDへの初回コピー後に書込みサービスを停止して最終差分を同期し、ファイル件数、総バイト数、チェックサムを照合する。照合とアプリケーション受入試験が完了するまで既存HDDを消去・再利用せず、読み取り専用のロールバック元として保管する。既存データがない場合、この移行工程は実施しない。

5. Quota設計

Quotaはアプリケーション層で管理し、保存前に現在使用量 + 新規サイズが上限を超えないことを確認する。Pilot初期値は100GB/Userを候補とし、Projectは50/100/500GB等を管理者が設定可能とする。UserとProjectの容量集計ルールを一意に定め、ファイルシステム全体の空き容量10%を運用予備として確保する。全体保護制限は個別Quotaより優先する。

if current_usage + incoming_size > hard_quota:
    reject upload/job output
elif usage_ratio >= 0.8:
    warn user/admin

6. Agent Sandbox設計

  • Agent実行ごとに一時Containerを起動。
  • 対象User/ProjectのWorkspaceのみ/workspaceへbind mount。
  • /mnt/storage全体はContainerへ公開しない。
  • Network、Shell、File Toolの権限をProfile化。
  • 実行時間、CPU、Memory、出力サイズに上限を設ける。

7. DeepSeek API設計

  • Provider層を抽象化し、将来他LLMを追加可能にする。
  • System Prompt、Project Context、User Requestを分離。
  • Tool Call結果は検証後にLLMへ返却。
  • API KeyはSecretとして保存し、DBやソースに平文保存しない。
  • 利用量・モデル・Token等をagent_runs/messagesへ記録。

9. ファイル安全設計

  • relative pathのみDB保存し、絶対パスの直接入力を禁止。
  • ..、symlink escape、Path Traversalを拒否。
  • 許可拡張子/MIME、最大ファイルサイズを設定。
  • アップロード名と保存名を分離しUUID等で保存可能にする。
  • Checksumを保持して重複・破損確認に利用。

11. 10TB HDD初期導入手順設計

  1. 対象が新規10TB HDDであることを型番・シリアル番号・容量で確認
  2. 必要に応じて初期健全性診断とS.M.A.R.T.確認
  3. GPTパーティション作成
  4. ext4フォーマット
  5. UUID確認
  6. /mnt/storage作成と所有者・権限設定
  7. /etc/fstabへUUID指定で登録
  8. mountpoint、期待UUID、読書き、再起動後の自動マウントを確認
  9. アプリケーションの起動依存と未マウント時の停止を確認
  10. Storage Monitorで容量・警告・エラー監視を確認

12. バックアップ/障害対策

新規10TB HDD 1台は単一障害点であり、故障・誤削除・ファイルシステム破損・筐体障害からデータを保護しない。Pilot期間中も重要Project、設定、DB、監査情報を10TB HDDとは別の媒体または別システムへ定期バックアップし、復元テストを行う。バックアップ先の容量、頻度、保持世代、暗号化、RPO/RTOはPilot開始前に確定する。既存4TB HDDは容量不足のため10TB全体の完全バックアップとはみなさず、再利用時は対象データを限定して健全性を確認する。
